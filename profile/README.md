## cotomu Enablement

御社の開発組織に加わり、機能が本番に届くまでの流れを止めている仕組みを整えます。機能を作るチームが前に出られるよう、CI/CD・インフラ・監視・セキュリティといった足元の仕事を引き受けます。

- **機能開発は担いません。** 機能を作るのは御社のチーム。私たちは開発の流れを支える仕組みと、その運用を受け持ちます
- **依頼するタスクを用意する必要はありません。** 課題を見つけるところから一緒に始めます
- **重要なのに後回しになる改善を、計画して進めます。** CI の高速化、ライブラリの計画的な更新、テストの整備、AI を使う開発の基盤づくりなど

書籍『チームトポロジー』でいう、機能を作るチーム（ストリームアラインドチーム）を支えるイネイブリングチームとプラットフォームチームの役割です。

## こんな状態なら相談してください

| 領域 | よくある状態 | 実際に変えたこと |
|---|---|---|
| CI | CI の待ち時間が長く、開発者の手が止まっている | デプロイ時間の中央値を 20.3分 → 8.7分 に短縮 |
| デプロイ | 本番に出せる人が限られ、その人がいないとリリースが止まる | 画面のボタンから誰でもリリースでき、すぐ戻せる形に |
| レビュー | レビュー待ちで、できあがった機能がなかなか出せない | プロジェクト固有の設計ルールを 12 個の独自検査にし、既存コードの見落とし 20 件を発見 |
| テスト | テストが不安定で、リリースのたびに確認に時間がかかる | モックに頼らず、本物のデータベースで確かめるテストに |
| 実装 | 開発環境の用意に時間がかかる | 環境の用意と定型の変更を、コマンド1つで流せる形に |
| 監視 | 障害をお客様からの連絡で知る | DB の負荷・バッチの失敗・CI の失敗をアラートでチャットに通知 |
| インフラ | 環境が手作業で作られ、作った人しか分からない | 変更内容を本番に出す前に確かめられる、失敗しにくい進め方に |
| クラウド費用 | 費用が増えた理由を誰も説明できない | 請求を項目ごとに調べ、使っていないデータの複製やバッチ 9 件を停止 |
| 性能 | 画面の表示や検索が遅く、お客様を待たせている | 遅い問い合わせを記録からたどり、原因から直す |
| セキュリティ | 権限やライブラリの点検が後回しになっている | ライブラリの緊急パッチを、公表の翌日に本番へ |
| AI 活用 | AI の使い方が人によってばらばら | AI への頼み方をチーム共通の手順にし、350 件超の定常的な変更を AI で取り込み |
| 体制 | 土台を見ていた人が辞め、仕組みの中身を誰も知らない | ずれていたインフラの定義を実機とそろえ、リリースや障害対応の手順を文書に |

## 専任を採用する代わりに

| | 社内で専任を採用する | cotomu Enablement に任せる |
|---|---|---|
| 始めるまで | 必要な専門性を持つ人を探して採用する | 改善の経験を持つチームに、すぐ相談できる |
| 費用 | 給与に加え、採用と立ち上がりの費用がかかる | 月額。採用と育成の負担なく改善を頼める |
| やり方 | 担当者が調べながら学ぶ | 経験から得た判断の軸で、迷いと手戻りを減らす |
| 機能開発との両立 | 担当や優先順位の調整が必要 | 社員の時間を、事業に固有の開発へ回せる |

## 進め方

1. **NDA を結び、現状を拝見** — リポジトリやチームの状況を見せていただきます
2. **契約前に課題と改善案をご提案** — 開発を妨げている原因と、何をどう変えるとよいかをお出しします
3. **一つの改善から始める** — いちばん効果の大きいテーマから始め、回り始めたら次のテーマへ広げます
4. **週1回の報告と、定例・チャットでの相談** — 進み具合、次に出すもの、判断してほしいことをまとめて報告します

**契約の条件**

- 契約の形: 準委任（最低1か月）
- 料金: 月額。プランと金額は資料でお送りします
- 契約を終えるとき: IaC のコード一式、CI/CD のパイプラインと設定、運用手順書と Runbook、監視とアラートの設定を社内に引き継ぎます
